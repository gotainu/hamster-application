# Ham Care 品質改善・RAG v2再設計計画

最終更新: 2026-09-12

## 目的

Google Playへの審査送信を一時保留し、日常利用で信頼でき、通知が煩わしくなく、AI回答から根拠と関連する過去動画へ自然に移動できる品質改善版を作る。

## 現状と主要課題

### 通知

- 現行の異常通知は主に24時間の重複防止で制御している。
- 同じ異常状態が継続すると、意味がほぼ同じ通知が翌日再送される可能性がある。
- 新規発生、継続、悪化、重大度上昇、解消、再発が十分に区別されていない。

### 健康スコア

- 環境35%、活動量25%、体重25%、今日の様子15%の加重平均を基礎としている。
- データが存在する領域だけで重みを再正規化するため、欠測の組み合わせによって点数の意味が変わる。
- 固定閾値、個体差、短期変化、長期傾向、データ信頼度が一つの点数へ混在している。
- 単一スコアが診断結果のように見えない表示上の配慮が必要である。

### RAG

- 約627チャンクのテキスト記事を埋め込み、Dense検索のTop-Kを回答生成へ渡している。
- 文単位・行単位のチャンク化で、質問意図、キーワード一致、複数論点、情報の新旧を十分に扱えない。
- YouTube動画のメタデータ、時間付き文字起こし、サムネイル、動画URLが検索結果モデルにない。
- Flutter側の応答は answer と chunks が中心で、出典カードや動画カードを第一級のデータとして扱っていない。

### 有料機能のテスト

- 現行の本番Stripe Checkoutから登録すると、クローズドテスターにも実際の請求が発生する。
- Google Play Billingのライセンステスター機能は現行のStripe経路には適用されない。
- テスターに決済を要求せず、有料機能を安全に検証できるサーバー管理の権限が必要である。

## 設計原則

1. 安全に関係する表示は、点数より状態、主因、推奨行動、データ信頼度を優先する。
2. 通知は定時ではなく意味のある変化を契機にする。
3. AI回答では、回答根拠と関連コンテンツを区別する。
4. YouTube動画は必ず提示できる契約にするが、直接の根拠でない動画を根拠として装わない。
5. エージェント化は検索品質を測定できるようになってから行う。
6. ベータ権限はサーバーだけが付与でき、期限切れと監査履歴を持つ。

## 通知v2

### 通知イベント

- 新規発生: 正常または未検出から注意・警戒へ変化した。
- 重大度上昇: 注意から警戒へ変化した。
- 有意な悪化: 同じ状態でも主要値が設定幅以上悪化した。
- 再発: 一度解消した状態が再び発生した。
- 継続リマインド: 長期間続き、直近の通知から十分な期間が空いた。
- 解消: ユーザーが希望した場合のみ送る。

### 初期案

- 警戒: 即時通知。継続中は12時間以内に再送しない。
- 注意・変化: 原則として初回のみ。継続リマインドは72時間後。
- 注意・変化の上限: 週2件。
- 同一状態で数値変動が小さい場合は再送しない。
- 夜間の静穏時間、カテゴリ別ON/OFF、頻度設定を設ける。
- 通知ログに eventType、previousState、currentState、metricDelta、suppressionReason を保存する。

## 健康スコアv2

### 表示モデル

- 総合状態: 良好、安定、変化あり、注意、警戒、データ不足。
- 領域別評価: 環境、活動量、体重、今日の様子、給餌。
- データ信頼度: 高、中、低、算出不可。
- 主な要因: 最大3件。
- 参考スコア: 十分なデータがある場合だけ表示する。

### 算出方針

- 固定の飼育目安と個体ベースラインを分離する。
- 絶対的な危険域は個体平均との差より優先する。
- 個体ベースラインは十分な記録日数を満たした後だけ使用する。
- 欠測時に残存領域だけで100点満点へ単純再正規化しない。
- 点数、状態、信頼度を別々に算出する。
- ルールごとに根拠、閾値、テストケースを残す。

## RAG v2

### 知識ソース

- 既存の記事チャンク。
- 所有するYouTubeチャンネルの動画メタデータ。
- 時間付き文字起こし。
- 将来追加する監修済みFAQ。

### YouTube文書モデル

- videoId
- title
- url
- thumbnailUrl
- publishedAt
- durationSeconds
- startSeconds / endSeconds
- transcriptText
- chapterTitle
- tags / topics
- sourceType: youtube_transcript
- contentVersion

動画URLは該当箇所から再生できる時間指定URLを生成する。

### インデクシング

1. 動画メタデータと字幕・文字起こしを取得する。
2. 章、話題転換、時間幅を考慮して30〜90秒程度のセグメントへ分割する。
3. 前後の文脈を保つため小さなオーバーラップを持たせる。
4. 記事と動画へ共通のトピック、対象、症状、環境要因、情報更新日を付与する。
5. Dense埋め込みとキーワード検索用インデックスの両方を作る。

### 検索パイプライン

1. 質問を意図、対象、時間軸、必要な安全性へ分類する。
2. 必要に応じて検索クエリを複数へ展開する。
3. Dense検索とキーワード検索を並行する。
4. 結果を統合し、再ランキングする。
5. 類似結果の重複を除き、記事と動画のカバレッジを調整する。
6. 根拠として使える箇所だけを回答生成へ渡す。
7. 回答の各主張と出典を対応付ける。
8. 関連動画を最低1件返す。直接根拠がない場合は supporting または general として区別する。

### API v2応答契約

- answer: 回答本文
- citations: 回答の主張に対応する記事・動画セグメント
- relatedVideos: 動画ID、タイトル、URL、サムネイル、開始秒、関連度区分、短い理由
- confidence: 回答根拠の充足度
- safetyNotice: 必要な場合の受診・緊急対応案内
- retrievalMeta: 検索バージョン、所要時間、候補数。通常UIでは非表示

### Flutter UI

- 回答直下に「根拠」と「関連動画」を分けて表示する。
- 動画カードはサムネイル、タイトル、該当箇所、関連理由を表示する。
- タップするとYouTubeの時間指定URLを開く。
- 根拠不足の場合は断定せず、追加質問または記録確認を促す。

## エージェント検索

RAG v2の評価が安定した後、次の限定された検索ループを追加する。

1. 質問を複数の調査項目へ分解する。
2. 初回検索結果の不足論点を判定する。
3. 最大2回まで再検索する。
4. 主張と根拠の対応を検証する。
5. 十分な根拠がなければ回答範囲を狭める。

初期上限は、最大3検索、最大1回の再ランキング、明示した時間・費用上限とする。無制限の自律ループは採用しない。

## ベータテスター権限

### 推奨モデル

- サーバー管理の beta_entitlements を設ける。
- uid、features、startsAt、expiresAt、grantedBy、reason、revokedAt を保持する。
- クライアントからの作成・更新をFirestore Rulesで禁止する。
- 有料判定は有効なStripe契約または有効なベータ権限のどちらかで許可する。
- UIには「ベータテスト用アクセス。請求は発生しません」と明示する。
- 期限終了時に自動失効し、Stripe顧客や購読を作成しない。

## 実装順序

1. 評価指標と受け入れ条件を確定する。
2. ベータ権限のデータモデルと権限境界を実装する。
3. 通知v2を実装し、既存ログを使った再生テストを行う。
4. 健康スコアv2を実装し、固定ケースと境界値を検証する。
5. YouTube取り込みパイプラインとRAG v2 APIを構築する。
6. 検索評価セットで旧RAGと比較する。
7. 動画カードを含むAI相談UIを実装する。
8. エージェント検索を追加して費用、速度、品質を再評価する。
9. 全体のUI/UX、E2E、通知実機試験を行う。
10. Google Playの審査送信とクローズドテストを再開する。

## 最初に確定する受け入れ条件

- 同じ注意状態で主要値がほぼ不変なら、翌日に同じ通知を送らない。
- 警戒への悪化は重複抑制中でも通知する。
- スコア画面から、点数を決めた領域、データ不足、主要因を確認できる。
- RAG評価質問の各回答に、根拠または根拠不足の明示がある。
- 各AI回答に関連動画カードが1件以上表示され、リンクとサムネイルが正しい。
- 動画が直接の根拠でない場合、関連動画として明確に区別される。
- ベータテスターは決済画面を通らず有料機能を利用でき、期限後は自動で無料状態へ戻る。
